## Key Points

- Tool output from systems like Jira, GitHub, and Salesforce is often mistakenly trusted because the system itself is trusted, but any field accepting free text (like ticket bodies or PR descriptions) should be considered untrusted
- Prompt injection attacks can bypass traditional security controls by using coerced calls - where a trusted agent's authorized capabilities are redirected toward attacker goals
- Coding assistants in remote development environments are particularly vulnerable because they read untrusted repository content while having access to privileged tools like shell execution and cloud credentials
- Traditional security screens (input screening, output screening, action screening) operate independently and can't detect the relationship between a poisoned tool result and the coerced call it produces
- The most effective defense involves behavioral baselining of individual agents to detect when they make calls they've never made before, especially after reading untrusted content
- Attackers must create a deviation from an agent's normal behavior for the attack to succeed, and this deviation can be detected by monitoring the agent's execution history
- Re-labeling tool inventory by field (not just by system) and ranking agents by the combination of untrusted fields they read and privileged tools they hold is critical for risk assessment
- The blast radius of prompt injection against coding assistants is determined by how many untrusted fields the agent reads and what privileged tools it can access
- Tool-output injection (in execution results) is more effective than tool poisoning (in descriptions) because results have higher recency in the context window
- A complete defense requires instrumenting both the tool result and the subsequent call, catching the pair in the few hundred milliseconds when they exist together in one agent turn
